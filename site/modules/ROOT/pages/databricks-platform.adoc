= How Neo4j + Databricks Work Together

Databricks and Neo4j are complementary platforms connected through governed data pipelines. Databricks governs and refines data at scale and answers aggregation questions through SQL. Neo4j makes the connections between entities explicit and answers traversal questions through Cypher. Delta Lake serves as the interchange format between them, the Spark Connector moves data in both directions, and Mosaic AI powers the agents that route questions to the right engine.

This page covers the architecture that joins the two platforms: the Lakehouse foundation, the Spark Connector bridge, and the six integration patterns that carry data and queries between the systems. The xref:index.adoc[workshop overview] has the dataset this architecture operates on and the lab roadmap. For hands-on implementation, see xref:lab2.adoc[Lab 2] for Spark Connector ETL, xref:lab3.adoc[Lab 3] for semantic search, and xref:lab4.adoc[Lab 4] for agents.

== Two Platforms, Two Query Shapes

Databricks answers "how much?" and "how often?" through SQL aggregation over rows and columns. Neo4j answers "how is this connected?" and "what is affected?" through Cypher traversal over nodes and relationships. Most real-world questions require both.

An aircraft maintenance investigation illustrates why. A fleet manager asks: "Which aircraft models have the highest EGT (Exhaust Gas Temperature) volatility, and what maintenance events are connected to those aircraft?" EGT is the standard engine health indicator, and its volatility is how a fleet manager spots an engine losing margin. xref:glossary.adoc[The glossary] has that term and the rest of the fleet vocabulary. The first half of the question is a `GROUP BY` with `STDDEV` over the `sensor_readings` table. The second half is a multi-hop traversal from Aircraft through System, Component, and MaintenanceEvent nodes. Neither platform can answer the full question alone. A supervisor agent decomposes the question, routes each half to the platform built for it, and synthesizes a single response.

.Databricks SQL: the aggregation half
[source,sql]
----
SELECT a.model, sen.type,
       AVG(r.value) AS avg_reading,
       STDDEV(r.value) AS volatility
FROM sensor_readings r
  JOIN sensors sen ON r.sensor_id = sen.sensor_id
  JOIN systems s ON sen.system_id = s.system_id
  JOIN aircraft a ON s.aircraft_id = a.aircraft_id
WHERE sen.type = 'EGT'
GROUP BY a.model, sen.type
ORDER BY volatility DESC
----

.Neo4j Cypher: the traversal half
[source,cypher]
----
MATCH (a:Aircraft)-[:HAS_SYSTEM]->(s:System)
      -[:HAS_COMPONENT]->(c:Component)
      -[:HAS_EVENT]->(m:MaintenanceEvent)
WHERE a.tail_number = 'N95040A'
  AND m.severity = 'CRITICAL'
RETURN s.name, c.name, m.description, m.event_date
ORDER BY m.event_date DESC
----

The split follows the shape of the question. Counting stays in SQL. Following connections moves to the graph. Questions that span both route to specialized agents. See xref:lab4.adoc[Lab 4] for how the supervisor implements this routing.

== Lakehouse Architecture

=== The Medallion Pattern

Data moves through three progressive refinement layers:

* **Bronze** is the raw landing zone. Aircraft CSV files arrive from cloud storage such as S3, ADLS Gen2 or GCS, with no transformation. This is the system of record for what was ingested and when.
* **Silver** is the curation layer. Schema enforcement catches malformed records, column renaming normalizes conventions, and type casting ensures consistency. Silver tables are governed and ready for downstream consumers, including the Neo4j Spark Connector. Graph-bound data gets its last quality check here before projection.
* **Gold** is where graph intelligence feeds back into the lakehouse. Graph algorithm results write back from Neo4j as columns in gold tables: PageRank scores for component importance, community detection clusters for related maintenance events, and degree centrality counts across the fleet topology. These join with sensor telemetry and fleet metadata that never left the lakehouse to produce maintenance alerts, risk scores, and ML feature tables.

=== Delta Lake

Delta Lake provides ACID transactions, schema enforcement, and time travel on top of cloud object storage. For this architecture, it serves as the interchange format between Databricks and Neo4j. The Spark Connector reads from governed silver tables and writes graph algorithm results back to gold tables. Schema enforcement upstream means the graph receives clean, typed data without additional transformation at load time. Time travel enables rollback when a pipeline run corrupts data, avoiding full re-ingestion.

== The Spark Connector

The Neo4j Spark Connector is the Databricks-certified bridge for bulk data movement. It reads silver Delta tables and writes them as graph nodes and relationships. The transformation follows a consistent pattern: table rows become nodes with column values as properties, foreign keys become relationships, and shared attribute values become shared nodes that make hidden connections explicit. An airport code appearing on many flights is one of those. The connector also reads from Neo4j back into DataFrames for validation and bidirectional data flow.

See xref:lab2.adoc[Lab 2] for a hands-on walkthrough loading the aircraft digital twin data, including the specific transformation patterns for each entity type.

== Six Integration Patterns

Six patterns connect Databricks to Neo4j, each suited to a different workload.

=== ELT Data Pipeline

Governed Delta tables project into graph nodes and relationships via the Spark Connector. Silver tables feed the connector; the connector writes nodes and relationships into Neo4j using batched upserts. This is the primary path for bulk loading structured data.

=== Virtual Graph

The ELT data pipeline moves data into Neo4j. The virtual graph leaves it in place. A schema map defines a graph model over existing Delta tables, and a virtual graph database translates Cypher into SQL that pushes down to the lakehouse. Rows become nodes, foreign keys become relationships, and the query executes where the data already lives. No ETL job runs and no second copy of the data exists in Neo4j.

The virtual graph registers the lakehouse as a graph source so Neo4j tooling queries Delta tables through Cypher. The full Neo4j Graph Intelligence Platform applies: Browser, Bloom, Copilot, and Graph Analytics operate against lakehouse data without a load step.

....
  Neo4j tooling (Browser, Bloom, GDS)
        │  Cypher
        ▼
  Virtual graph ──── translates Cypher to SQL ────▶ Delta tables
        ▲                                            (data stays in lakehouse)
        └──────────── results as nodes / relationships ──┘
....

Four properties define the pattern:

* **Zero data movement**: data stays in the lakehouse under its existing storage and lifecycle.
* **Full pushdown**: Cypher compiles to SQL and computation runs in the lakehouse engine where the data lives.
* **Standard protocols**: Bolt and JDBC connect existing tools without changes.
* **Your governance**: Unity Catalog access policies on the underlying tables continue to apply.

The virtual graph suits exploration and analysis over data that already lives in the lakehouse, where the cost or latency of a full projection is hard to justify. When traversal performance at scale, write-back of graph algorithm results, or a persistent operational graph matters, the ELT data pipeline remains the right path.

=== SQL Federation over the Graph

The virtual graph queries the lakehouse as a graph. SQL federation is the mirror image: it queries the graph as SQL, and the data stays in Neo4j.

The point is who gets to ask. An analyst who writes SQL every day and has never seen Cypher can query the graph directly, from a notebook, from Power BI, or through a Genie Agent. Nobody learns a second query language, and no copy of the graph lands in the lakehouse first.

The https://github.com/neo4j-labs/neo4j-unity-catalog-connector[Neo4j Custom JDBC Unity Catalog Connector] does the translating. It is a driver you install once: upload it to a Unity Catalog Volume, then register Neo4j as a `TYPE JDBC` connection. After that the driver rewrites incoming SQL as Cypher, so node labels behave like tables and node properties behave like columns. `SELECT COUNT(*) FROM Aircraft` reaches the graph as `MATCH (n:Aircraft) RETURN count(n)`.

....
  BI tools (Power BI, Tableau) / Genie Agents / notebooks
        │  SQL
        ▼
  Neo4j Custom JDBC
  Unity Catalog Connector ──── translates SQL to Cypher ────▶ Neo4j graph
        ▲                                                     (graph stays in Neo4j)
        └────────────── results as rows / columns ────────────┘
....

Queries go through `remote_query()`, a SQL function that sends a query through a connection and hands the answer back as a table. Because the answer is a table, one statement can join it to Delta tables:

[source,sql]
----
SELECT operator, flight_count
FROM remote_query('neo4j_connection',
    query => 'SELECT operator, COUNT(*) AS flight_count
              FROM Flight
              GROUP BY operator
              HAVING COUNT(*) > 0'
)
ORDER BY flight_count DESC
----

The `GROUP BY` runs inside Neo4j, so one row per operator crosses the wire instead of one row per flight. The `HAVING COUNT(*) > 0` does not change the result. It works around a caching bug that can return an empty set for a plain `GROUP BY` on a warm cluster, and it is worth keeping in every federated aggregation you write.

Four properties define the pattern:

* **Zero data movement**: the graph stays in Neo4j under its existing storage and lifecycle.
* **Pushdown**: filters, aggregates, sorts, and joins translate into Cypher and run in Neo4j.
* **No Cypher required**: any SQL client that reaches Unity Catalog reaches the graph.
* **Your governance**: the connection carries Unity Catalog credentials, permissions, and audit.

Neo4j's schema can also be published into Catalog Explorer, so graph labels are listed beside Delta tables and a Genie Agent can answer questions about them in plain English.

One cost shapes where this fits. Databricks runs custom drivers inside an isolated sandbox, which needs a memory setting raised and adds seconds to every query. That suits interactive analysis and BI, and rules out anything latency-sensitive. For bulk movement or a persistent operational graph, the ELT data pipeline is still the right path.

Custom-driver JDBC connections reached Public Preview at Databricks Runtime 18.1 and Databricks SQL 2025.40. Below that, two preview features have to be switched on per workspace. No lab in this workshop builds this pattern; https://neo4j-partners.github.io/neo4j-uc-connector-demos[the connector demos] carry runnable notebooks.

=== Knowledge Graph Construction

Maintenance manuals, technical bulletins, and regulatory filings pass through a knowledge graph construction pipeline. Documents split into chunks, embedding models convert chunk text into vectors, and LLM-based entity extraction pulls structured nodes from the text. The `neo4j-graphrag-python` library's SimpleKGPipeline handles this pipeline using the Neo4j Python driver directly, because chunking and entity extraction are single-machine work rather than Spark operations. Extracted entities cross-link to the operational graph built by the data pipeline, bridging maintenance knowledge and fleet structure.

=== Data Analytics: Graph as Co-Processor

Graph algorithms run on in-memory projections in Neo4j and write results back to gold Delta tables through the Spark Connector:

* **PageRank** produces importance scores for components.
* **Community detection (Louvain)** identifies clusters of related maintenance events.
* **Degree centrality** counts connection density across the fleet topology.

These graph-derived metrics become columns in Delta tables, available for dashboards, ML features, and downstream analytics.

Where the Spark Connector carries algorithm results back as tables, <<sql-federation-over-the-graph,SQL federation>> reads the graph in place, so BI tools and notebooks join graph results with lakehouse data without leaving SQL.

=== GraphRAG and Agents: Multi-Platform Retrieval

Specialized agents query each platform independently. The Neo4j MCP agent discovers the graph schema through `get_neo4j_schema` and executes read-only Cypher through `read_neo4j_cypher`. The Genie Agent translates natural language into SQL against the lakehouse. A supervisor agent routes questions based on their nature: aggregations and trends go to the Genie Agent, relationships and traversals go to the graph agent, and questions that span both platforms decompose into sub-tasks before the supervisor synthesizes a combined answer.

[cols="1,2,2"]
|===
| Stage | Connector | Use Case

| Data Pipeline

| Virtual Graph
| Neo4j virtual graph (Bolt + JDBC)

| KG Construction

| Data Analytics
| Neo4j Spark Connector

| Neo4j Custom JDBC Unity Catalog Connector

| Neo4j MCP Server + Python driver
| Schema discovery, Cypher execution, vector search, agent tool access
|===

== Unity Catalog

For the GraphRAG architecture, Unity Catalog plays two specific roles:

* **Governance of graph-bound data**: the silver tables that feed the Spark Connector are governed assets with lineage tracking. When graph data quality issues surface, lineage traces back through the exact transformations and source records that produced the data.
* **Federated access to Neo4j**: the Neo4j Custom JDBC Unity Catalog Connector registers the graph as a `TYPE JDBC` connection, so federated queries that combine graph relationships and lakehouse metrics run under the same credentials, permissions, and audit as any other lakehouse query. <<sql-federation-over-the-graph,SQL Federation over the Graph>> above has the mechanics.

Grants on that path stop at the connection. Access is given on the connection as a whole rather than on individual node labels, so anyone who can use it can read the whole graph behind it. Neo4j is not an officially supported federation source yet, and official status is what would bring per-table grants, a browsable foreign catalog, and column-level lineage. The xref:slides/slides-neo4j-connectors.adoc[Neo4j Connectors deck] covers how that connection is built and what it can read, and the xref:slides/slides-auth-sync.adoc[Authorization Sync deck] covers the gap in full.

== Agent Systems

Databricks provides the agent development and serving stack through Mosaic AI, from foundation model access to multi-agent orchestration:

* **Foundation models** through the AI Gateway handle embedding generation for vector search and the reasoning layer that agents use to select tools and synthesize answers.
* **Genie Agents** translate natural language into governed SQL against any data registered in Unity Catalog. Domain experts configure Genie Agents with curated table sets, domain terminology, and example queries. In this architecture, a Genie Agent handles the sensor telemetry half of the multi-agent system: questions about averages, trends, and fleet-wide comparisons route to the Genie Agent, which generates SQL against the lakehouse. All generated queries are read-only.
* **Agent Bricks** is the control plane for deploying and orchestrating agents. The supervisor agent pattern is configurable through the workspace UI: register sub-agents, which can be Genie Agents, MCP servers or Unity Catalog functions, provide a capability description for each, and the supervisor routes questions based on their nature. Agents package with MLflow, register in Unity Catalog, and deploy to Model Serving endpoints that scale automatically. Built-in tracing and feedback collection through the Review App support production monitoring.

See xref:lab4.adoc[Lab 4] for the hands-on implementation of the Genie Agent, the Neo4j MCP agent, and the supervisor.

== Agent Memory

Where Mosaic AI provides the agent development and serving stack, Neo4j contributes memory to the agents that run on it. Agent memory is a capability the supervisor and its sub-agents use, not a new connection between the platforms. It exposes three functions through the same agent-tool mechanism the Neo4j MCP agent already uses:

* **Short-term memory** holds working context within a session: recent turns, intermediate results, and the state the supervisor carries while it decomposes a multi-platform question and waits on its sub-agents.
* **Long-term memory** persists across sessions as a graph of facts, entities, and the relationships between them. An agent recalls prior findings and connects them to new ones by traversing that graph at retrieval time. Storing memory as a graph fits the shape of the data: memory is relational, and the connections between remembered facts are themselves what the agent reasons over.
* **Decision traces** capture the agent's routing choices, tool calls, and reasoning as a connected graph. Each decision links to the context that produced it, which supports auditability and lets later decisions reason over earlier ones.

Decision traces are distinct from the MLflow tracing in Agent Bricks. MLflow tracing is observability for monitoring runs and collecting feedback. Neo4j decision traces are a queryable graph the agent traverses at runtime and builds long-term memory from. The two are complementary: one watches the agent from the outside, the other gives the agent a memory it can reason over.

Agent memory plugs into Agent Bricks the same way the other sub-agents do. The supervisor reads and writes memory through agent tools, so no new connection type is introduced.
