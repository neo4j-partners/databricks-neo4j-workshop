.**At a Glance**

== Graph Databases

A graph database models data as nodes and relationships. Nodes represent entities. Relationships represent the connections between them. Both carry properties, which are key-value pairs that describe their attributes.

The notation follows a visual convention. Parentheses denote nodes, brackets denote relationships:

----
(:Component {name, type})-[:HAS_EVENT {date, severity}]->(:MaintenanceEvent)
----

Each Component node carries properties like name and type. Each HAS_EVENT relationship carries details like date and severity. The relationship is directional, typed, and stored as a first-class element alongside the nodes it connects.

.How graphs compare to relational databases
[%collapsible]
====
Relational databases represent connections implicitly, through foreign keys and join tables. Graphs store them explicitly, as relationships you can traverse. A question that follows a chain of connections becomes a single traversal pattern in Cypher, where SQL needs a nested join per hop.
====

image::lab1-property-graph.svg[Aircraft Digital Twin property graph showing Aircraft, System, and Maintenance nodes connected by typed relationships]

.Graph Insight: Maintenance Impact Chain
[%collapsible]
====
A single maintenance event connects to both the affected engine _and_ the aircraft through typed relationships (`AFFECTS_SYSTEM`, `AFFECTS_AIRCRAFT`). This triangle of connections means you can start from any node and traverse to the others: "Which aircraft have critical faults?" or "What maintenance events affect Engine #1?" Queries that would require multiple JOINs in a relational database are single traversal patterns in the graph.
====

Cypher is the query language for interacting with Neo4j. It uses a pattern-matching syntax that mirrors the visual structure of nodes and relationships, making graph queries readable as descriptions of the data they retrieve:

[source,cypher]
----
MATCH (a:Aircraft)-[:HAS_SYSTEM]->(s:System)-[:HAS_COMPONENT]->(c:Component)
WHERE a.tail_number = 'N95040A'
RETURN s.name, c.name
----

.How the query works
[%collapsible]
====
The query reads like the pattern it matches: start at an Aircraft node, follow HAS_SYSTEM to a System, then HAS_COMPONENT to a Component. Cypher handles multi-hop traversals and path-finding operations natively.
====

== The Aircraft Digital Twin Graph

The workshop builds a knowledge graph representing aircraft digital twins. Five core entity types and the relationships between them capture the structure of an aircraft fleet, its operations, and its maintenance history:

[cols="1,3"]
|===
| Entity Type | Examples

| **Aircraft**
| Boeing 737-800, Airbus A320/A321, Embraer E190

| **Systems**
| Engines, Avionics, Hydraulics

| **Components**
| Turbines, Compressors, Pumps

| **Flights**
| Flight operations with departure/arrival airports

| **Maintenance Events**
| Fault tracking with severity levels
|===

These entities connect through typed relationships that reflect real-world structure:

----
(Aircraft)-[:HAS_SYSTEM]->(System)-[:HAS_COMPONENT]->(Component)
(Aircraft)-[:OPERATES_FLIGHT]->(Flight)-[:DEPARTS_FROM]->(Airport)
(Component)-[:HAS_EVENT]->(MaintenanceEvent)
----

A question like "Which components caused flight delays for aircraft N95040A?" requires traversing from Aircraft through Flight to Delay, then back through MaintenanceEvent to Component. That multi-hop traversal is what the graph handles natively.

image::dual-database-architecture.svg[Dual-database architecture showing Neo4j and Databricks working together for the Aircraft Digital Twin]

.Dual-database architecture
[%collapsible]
====
The Aircraft Digital Twin spans two platforms. Neo4j holds the topology: how aircraft, systems, components, flights, and maintenance events connect. Databricks holds the volume: high-frequency sensor telemetry, fleet-wide aggregations, and governed Delta tables. Aircraft, systems, and sensors exist in both databases as join points, enabling queries that combine graph traversal with analytical computation.
====

== Neo4j Aura

Neo4j Aura is a fully managed cloud graph database service. It provides the Neo4j graph engine without the operational overhead of running infrastructure: automatic backups, high availability, and deployment across AWS, GCP, and Azure. Each participant provisions their own Aura instance to hold the Aircraft Digital Twin graph. That one instance carries through the whole workshop: Lab 2 loads it, Lab 3 enriches it, and Labs 5 and 6 query and write to it.

.The limits of AuraDB Free
[%collapsible]
====
The workshop runs on **AuraDB Free**, not the 14-day trial and not Professional. Free never expires, so your instance is still there between sessions.

It holds up to **200,000 nodes and 400,000 relationships**. Everything the labs load fits well inside that, because the sensor readings live in Databricks rather than in Neo4j.

Free does not include **Graph Data Science**, the library of algorithms like PageRank and community detection. No required lab uses it. xref:lab2.adoc[Lab 2]'s `02_gds_knn_aircraft.ipynb` and the GDS appendix are take-home material: read them during the workshop, run them later on an instance that has the plugin.
====

.Vector search and AI capabilities
[%collapsible]
====
Aura provides capabilities beyond the core graph engine that support AI retrieval pipelines directly:

* **Built-in vector indexes** store embeddings alongside graph data, enabling semantic similarity search without a separate vector store.
* **Combined vector and graph queries** retrieve documents by semantic similarity in a single Cypher operation, then follow relationships to pull in structural context.

Both are on Free, and both come together in xref:lab3.adoc[Lab 3], semantic search over maintenance manuals.
====

== Aura Developer Tools

The Aura console provides three tools you will use throughout the workshop:

* **Query Workspace** is a developer environment for writing and executing Cypher queries with syntax highlighting, auto-completion, and saved query collections. You will use this to verify data loads and explore results.
* **Explore**, powered by Neo4j Bloom, provides visual graph exploration through an interactive canvas. Search for nodes by label or property, expand their relationships, and discover patterns visually. Natural language search translates questions into graph queries without writing Cypher.
* **Dashboards** offer low-code data visualization including bar charts, geographic maps, and 3D graph visualizations for presenting graph data to non-technical stakeholders.
