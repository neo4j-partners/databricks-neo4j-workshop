= Lab 3: Semantic Search for Aircraft Maintenance

Lab 2 loaded structured data into Neo4j: aircraft, systems, components, sensors, flights. The graph captures topology and operational history, but it cannot answer questions about maintenance procedures, troubleshooting steps, or fault diagnostics. That knowledge lives in unstructured documentation. Lab 3 bridges this gap by ingesting the A320-200 Maintenance Manual into the knowledge graph and enabling semantic search over it.

TIP: Ready to start? Open `Lab_3_Semantic_Search/01_data_and_embeddings.ipynb` in your Databricks workspace, then work through `02_graphrag_retrievers.ipynb`. Every step lives in those notebooks; this page is the background behind them.

.**At a Glance**

* **Embeddings** convert text to numerical vectors that capture meaning: "engine overheating" and "thermal runaway in turbine" match by similarity, not keywords
* **SimpleKGPipeline** chunks the maintenance manual, extracts entities, generates embeddings, and stores everything in Neo4j
* **GraphRAG** adds graph traversal after vector search: chunks anchor the search, then Cypher gathers connected entities and relationships
* **Four retrievers**, two search methods (vector, hybrid) times two return shapes (chunk text, chunk plus graph traversal)
* **Databricks Foundation Model APIs** provide hosted embedding and LLM models (BGE-large, Claude Sonnet 5)

== Embeddings and Vector Search

Embedding models read text and produce numerical vectors that capture what the text means, not just what it says. "Engine overheating" and "thermal runaway in turbine" produce similar vectors because they mean similar things, even though they share no keywords. This enables semantic similarity search: given a question, find the stored text whose meaning is most similar.

.How vector search powers RAG
[%collapsible]
====
Vector search is what makes RAG work. The system embeds a question, searches for the closest chunks in vector space, and feeds those chunks to the LLM as context. The next step is preparing documents for this process.
====

== From Documents to a Knowledge Graph

The `neo4j-graphrag` Python package provides `SimpleKGPipeline` to orchestrate the full transformation from raw text to a queryable knowledge graph. The pipeline reads the maintenance manual, chunks it, uses an LLM to extract entities and relationships, stores the results in Neo4j, and generates vector embeddings for semantic search.

=== Documents to Chunks

Documents split into Chunk nodes with raw text, linked to their source Document via `FROM_DOCUMENT` and to adjacent chunks via `NEXT_CHUNK` to preserve reading order. An embedding model converts each chunk's text into a vector. A vector index over these embeddings enables semantic search by meaning rather than keyword matching.

.Chunking trade-offs
[%collapsible]
====
Larger chunks give the LLM more context during entity extraction, improving its ability to resolve references like "the engine" to a specific component. Smaller chunks produce more precise retrieval results, returning only the relevant passage rather than a block of mixed content. A moderate chunk size (500-1000 characters) with overlap at boundaries is a reasonable starting point, tuned by evaluating results.
====

=== Chunks to Graph Structure

An LLM reads each chunk and extracts entities: regulations, thresholds, procedures, components. These become graph nodes linked to their source chunks via `FROM_CHUNK`. Entity resolution deduplicates: the same regulation mentioned across five different chunks becomes one node with five links, not five separate nodes. Cross-linking connects extracted entities to the existing operational graph built in Lab 2, so a procedure that applies to a specific system links directly to that system's node.

.Schema design and entity resolution
[%collapsible]
====
* **Schema design.** SimpleKGPipeline supports three schema modes. **User-Provided** means you define the entity and relationship types. **Extracted** lets the LLM discover the schema. **Free** applies no constraints at all. This workshop uses User-Provided because the aircraft domain has known entity types (Aircraft, System, Component, Sensor, MaintenanceEvent) and known relationship patterns. Constraining extraction to these types produces a consistent, queryable graph.
* **Entity resolution.** The same real-world component can surface under different names ("HP Turbine," "High-pressure Turbine," "HPT"). Entity resolution merges these duplicates so that queries return complete results. Without it, maintenance event counts and relationship traversals silently miss data.
====

== GraphRAG: Graph-Enriched Retrieval

Vector or fulltext search finds the chunks most relevant to the user's question. That's standard RAG. GraphRAG adds graph traversal from those chunks through the entities and relationships surrounding them.

image::lab3-graphrag-retrieval-flow.svg[Aircraft maintenance GraphRAG retrieval flow showing vector/hybrid search through chunk, document, aircraft topology, and operating limit traversal to graph-enriched context]

.How GraphRAG retrieval works
[%collapsible]
====
A user question enters as text, and vector or fulltext search finds the matching Chunk nodes. Graph traversal then follows the entities and relationships surrounding those chunks, gathering the specific components, maintenance events, and systems connected to them. The result is graph-enriched context that reaches the agent or LLM, not just the chunk text. Without extracted entities linked to chunks and cross-linked to the operational graph, there would be nothing for the traversal to follow.
====

== Two Ways to Search Text

Every retriever in this lab starts by finding chunks. Two search methods do that job, and they fail in opposite directions:

* **Vector search** matches by meaning. "Engine running too hot" finds the chunk about thermal limits even when the two share no words. It is weak on exact strings: `V2500`, `925`, a part number or a fault code get blurred into general meaning rather than matched literally.
* **Fulltext search** matches by word. This is classic keyword search, and it is strong at exactly what vector search is weak at: codes, numbers, part names, the manual's own abbreviations. It is weak when the question's words differ from the manual's.
* **Hybrid search** runs both and merges the two ranked lists. It covers both failure modes at once.

Notebook 01 builds two indexes over the same Chunk nodes for this reason: `maintenanceChunkEmbeddings` for vector search and `maintenanceChunkText` for fulltext search. Hybrid retrievers read both.

== The Four Retrievers

The `neo4j-graphrag` package gives this lab four retrievers. They are a two-by-two: how the chunk is found (vector or hybrid) times what comes back (chunk text, or chunk text plus a graph traversal).

[cols="2,2,2,1"]
|===
| Retriever | Finds chunks by | Returns | Notebook

| `VectorRetriever`
| meaning
| chunk text
| 02

| `VectorCypherRetriever`
| meaning
| chunk plus a graph traversal
| 02

| `HybridRetriever`
| meaning and keywords
| chunk text
| 03

| `HybridCypherRetriever`
| meaning and keywords
| chunk plus a graph traversal
| 03
|===

* **VectorRetriever** performs pure semantic search. It converts the user's question to an embedding, finds the most similar chunks by vector index lookup, and returns their text. This works well for conceptual questions like "How do I troubleshoot engine vibration?" where the answer lives within the matched chunks themselves.
* **VectorCypherRetriever** adds a graph traversal step after vector search. It finds semantically similar chunks the same way, then executes a custom Cypher query that traverses from each matched chunk to related entities in the graph. The chunk acts as an anchor: vector search determines relevance, then Cypher gathers the structured context around it. This is the retriever Lab 5's `graphrag_node` uses.
* **HybridRetriever** is VectorRetriever with fulltext search added. It queries the vector index and the fulltext index, merges the results, and returns chunk text. Reach for it when questions carry engine designations, fault codes or numeric thresholds.
* **HybridCypherRetriever** is the combination of both ideas: hybrid search finds the chunks, then a custom Cypher query traverses out from them. Notebook 03 uses it to walk `Chunk -> Document -> Aircraft -> System -> Sensor -> OperatingLimit`, returning the authoritative limit as structured fields rather than prose.

.When to use which retriever
[%collapsible]
====
The key constraint: traversal starts from what search found. If the question does not surface relevant chunks, no amount of graph traversal compensates. Questions targeting a specific entity by name ("How many faults affect AC1001?") may be better served by direct Cypher queries.

Questions carrying a code, a part number or a threshold favor the hybrid pair, because the fulltext component catches the literal token that vector search would smooth over. Notebook 03 runs the same three questions through `VectorRetriever` and `HybridRetriever` side by side so you can see the difference in the scores.
====

== Sample Questions

After completing this lab, you can ask questions like:

* "How do I troubleshoot engine vibration?"
* "What are the EGT limits during takeoff?"
* "What causes hydraulic pressure loss?"
* "When should I replace the fuel filter?"
* "What oil analysis levels indicate bearing wear?"

`EGT` is Exhaust Gas Temperature, the parameter these manuals set takeoff limits on. The answers come back in the manuals' own vocabulary, so expect terms like HPT, FADEC, and ATA chapter alongside it. xref:glossary.adoc[The glossary] expands all of them.
