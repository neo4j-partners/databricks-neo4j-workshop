= Lab 5: The LangGraph Supervisor Agent

Lab 4's optional demo showed a supervisor built from a form. This lab builds the same routing behaviour in code, against your own graph, and deploys it as your own endpoint. It uses the pieces the previous four labs produced: the Genie Agent from Lab 4, the fleet graph from Lab 2 and the GraphRAG retrievers from Lab 3, all reachable from one question.

.**At a Glance**

* **LangGraph** models the agent as a **state graph**: nodes that read and write a shared state object, and edges that decide what runs next.
* **One supervisor node, three tool nodes.** `genie_node` for SQL over Delta telemetry, `cypher_node` for traversal over your own Aura instance, `graphrag_node` for a `VectorCypherRetriever` over the Lab 3 manual chunks.
* **Every tool returns to the supervisor**, which can then pick another tool. That return edge is what makes this a supervisor rather than a router.
* **The routing rules live in the prompt.** Two of them were each written to fix a specific failure seen in testing.
* **A direct Bolt driver**, not an MCP server. The demo's MCP connection is an admin-managed Unity Catalog object, and one per participant is not a thing a classroom can stand up.
* **Deployment is a separate step.** The agent is logged to Unity Catalog and served as an endpoint that authenticates as a **service principal** rather than as you.

== The Shape of the Agent

image::lab5-agent-topology.svg[The Lab 5 supervisor routing to a Genie node, a Cypher node and a GraphRAG node over the Databricks Lakehouse and your own Aura instance,align=center]

A router picks one tool and is done. This supervisor sees what came back and gets to pick again, so a single question can use three tools in sequence with each choice informed by the last result. Nothing here writes to the graph.

=== The three tools

**`genie_node`** asks your Genie Agent, which writes SQL over the four Lakehouse tables and runs it. This is the only tool that can see a sensor reading. Your graph has `Sensor` nodes with no readings on them, because timestamped values at that volume belong in Delta, where scanning them is cheap.

**`cypher_node`** generates Cypher from the question and runs it in a read transaction. The schema it is given is the one your graph actually has, which matters: a schema promising nodes that are not there produces queries returning zero rows and an agent that reports it found nothing. A failed query gets one retry with its error message attached, because most text-to-Cypher failures are a mistyped property or a relationship pointing the wrong way, and the error says which.

**`graphrag_node`** is the Lab 3 retriever wrapped as a node. The question is embedded, the vector index returns the closest manual chunks, and a Cypher tail runs from each hit.

.What the Cypher tail adds
[%collapsible]
====
The tail walks sideways along `NEXT_CHUNK`, so a procedure split across a chunk boundary arrives whole, and upward through the `Document` to the aircraft the manual applies to. Neither of those facts is in the embedding, and both are one hop away in the graph. That is what GraphRAG adds over plain vector search, and it is why Lab 3 comes before this lab.
====

== Routing Lives in the Prompt

The wiring is about thirty lines of Python. The prompt is what decides which tool runs. Two of the three tools end in a Neo4j traversal, so a prompt that describes its tools by what they do at the *end* cannot tell those two apart. It sends manual questions to Cypher, where they return nothing, because manual text is not a property you can filter on.

The prompt routes on where the question **starts** instead:

* If it starts with a name you could put in a `WHERE` clause, `cypher_node` takes it.
* If it starts with a phrase you would search a manual for, `graphrag_node` takes it.

The two rules below were each added after a specific failure. Both are worth reading before you write your own routing prompt.

=== The direction rule

An `AFFECTS_AIRCRAFT` arrow written backwards matched nothing and returned zero rows with no error, on an aircraft that has 23 maintenance events. The tool reported that it found none.

.The fix, and the simpler one that was rejected
[%collapsible]
====
`AFFECTS_AIRCRAFT` and `AFFECTS_SYSTEM` both run **from** the `MaintenanceEvent` **to** the thing affected. A question naming an aircraft does not mean the arrow leaves the aircraft, so the events for a tail number are reached by matching `(:MaintenanceEvent)-[:AFFECTS_AIRCRAFT]->(:Aircraft {tail_number: ...})`. Written the other way round, the arrow points away from the named noun.

The simpler fix is to drop the arrow direction from the query and let it match either way. That was rejected, because it teaches a Cypher habit Lab 1 argues against and it makes every traversal in the workshop more expensive. The fix used instead is nine lines of schema text in the prompt, stating the direction and naming the failure it prevents.

**The fix belongs in the prompt, not the graph.** A wrong answer from a text-to-Cypher tool is usually a gap in what the model was told about the graph rather than a flaw in the graph itself.
====

=== The refusal rule

Asked which aircraft had the highest average vibration, the tool answered with `maxValue` `3.0` from the `Vibration - B737-800` operating limit. That number is a takeoff ceiling every B737-800 shares, transcribed from a manual. It is not a reading, it is not an average, and it is not that aircraft's.

.What the rule says, and why refusing is the right behaviour
[%collapsible]
====
The prompt now tells `cypher_node` to return exactly `RETURN 'The graph holds no sensor readings.' AS cannot_answer` for any question about a measured value, and never to substitute a limit, a threshold or a ceiling for a measurement.

Refusal is the useful behaviour because the supervisor is still holding the question. A refusal routes it to `genie_node`, which can answer it. A plausible wrong number ends the conversation with a confident falsehood, and nothing downstream can tell that it happened.

`OperatingLimit` catches the model out because the data is clean: exactly twenty canonical limits, never empty, never duplicated. A plausible number is always there to return, so the model reaches for it instead of admitting the graph has no reading.
====

== The Anchor Question

____
Which engines are showing abnormal EGT readings, what maintenance history do those aircraft have, and what does the maintenance manual say to do about high EGT?
____

One question, three tools, one answer. It routed `genie_node`, then `cypher_node`, then `graphrag_node`, in a single pass.

Genie named the engines carrying abnormal EGT. The graph returned the maintenance history for those aircraft, including a bearing wear fault with its corrective action. The manual closed with the guidance for high EGT: trend data for margin degradation, oil spectrographic analysis, fuel filter differential pressure, and a borescope of the HPT nozzle and blades, with corrective actions graded from minor to critical.

No single store holds all three answers. The telemetry is in Delta, the maintenance history is in the graph, and the guidance is in the manual chunks. That is why the workshop uses both platforms.

== Credentials, and What Happens Without Them

The notebook reads your Aura password from the secret scope Lab 3 wrote. **On the normal path no plaintext password is ever typed**, not into a cell, not into a config file, and it is not in the logged model. The deployed endpoint gets the same secret through its environment block, resolved when the endpoint starts. If the scope is missing, notebook 01 has a commented-out fallback cell you fill in by hand, which is the one place a password appears in the clear. Use it to get moving, then create the scope and clear the cell.

The agent also degrades rather than failing. If the `maintenanceChunkEmbeddings` vector index is missing, because Lab 3 notebook 01 was skipped, the builder detects it and drops `graphrag_node` from the available tools instead of raising at import. The graph still compiles and the agent still answers from telemetry and the fleet graph. Running Lab 3 notebook 01 brings the third tool back with no other change.

== Deploying the Agent

The second notebook logs the same graph to Unity Catalog as an MLflow `ResponsesAgent` and serves it as a Model Serving endpoint. The part to understand is which identity the endpoint runs as.

**It authenticates as a service principal, not as you.** In the notebook, the agent reaches Genie, the warehouse and the tables because your own account already has access to them. The endpoint has its own identity, and that identity starts with access to nothing. Every resource the agent touches has to be granted to it.

.Three things that follow from that
[%collapsible]
====
**Databricks resources and outside credentials are handled two different ways.** The Databricks objects the agent uses, meaning the Genie Agent, the SQL warehouse, the eight gold tables and the two model endpoints, are listed at log time in `build_resources`. Databricks grants the serving principal access to each item on that list. Aura is not a Databricks object, so it cannot go on the list. It is passed as environment variables holding `{{secrets/<scope>/<key>}}` references, which the endpoint resolves from your secret scope when it starts.

**Granting the Genie Agent does not grant the SQL warehouse under it.** A model logged with the Genie Agent but not the warehouse deploys fine and routes correctly, then answers every sensor question with `is not authorized to use or monitor this SQL Endpoint`. They are two separate resources and each needs its own entry in the list.

**Pin the requirements.** If you let MLflow infer them, it reads the packages installed on the cluster. A cluster carrying the Lab 6 memory wheel produces a requirement that pip cannot find, so the container fails to build about fifteen minutes later.
====

A first deploy takes roughly sixteen minutes, and the notebook polls and prints where it got to. It then asks the endpoint the same questions and scores the answers with MLflow's judges.

The registered model name and the endpoint name come from `agent.py` rather than from a string you type, because Lab 6 redeploys **this** endpoint rather than standing up a second one.

== Why a Bolt Driver Rather Than MCP

Lab 4's optional demo reached Neo4j through an MCP server registered as a Unity Catalog HTTP connection. That is the right shape for a governed, shared, admin-managed instance, and the wrong shape for a classroom: the connection is an admin object, one per participant instance is not something a workshop can provision, and the OAuth2 credential behind it belongs to whoever owns the server.

Your instance is yours, your password is in your secret scope, and the Neo4j Python driver opens a Bolt session against it in one line. The governance the demo shows is worth the setup once an instance has several users and several agents reaching it. With one user and one agent, it costs more than it returns.
