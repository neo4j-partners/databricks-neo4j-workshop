= Lab 6: Agent Memory

The Lab 5 agent answers one question at a time. Ask it about `N10011`, then ask "any maintenance events on that aircraft?", and it has no idea what *that* means. Close the notebook and everything it worked out is gone. This lab gives it a memory, and puts that memory in the same Aura instance the fleet already lives in.

Putting the memory in the same instance is what this lab is about. Most memory products keep conversations in a store of their own, so "which aircraft do people keep asking about" and "which aircraft is actually failing" end up in two systems that someone has to join by hand. Here a remembered aircraft **is** the `Aircraft` node Lab 2 loaded, so one `MATCH` walks from a technician's question to a maintenance record.

TIP: Ready to start? Open `Lab_6_Agent_Memory/01_agent_memory.ipynb` in your Databricks workspace. Every step lives in that notebook; this page is the background behind it.

.**At a Glance**

* **Two nodes added, three tools untouched.** `recall` before the supervisor, `remember` after synthesis. The supervisor is Lab 5's node with a `\{recalled}` block in front of its prompt.
* **Adoption is what makes it one graph.** The fleet's `Aircraft` nodes gain the `:Entity` label, so a message points at the aircraft rather than at a copy of it.
* **Adopt `Aircraft` and nothing else.** Adoption overwrites `type`, and four other labels already use that property for something.
* **Explicit mentions, not LLM extraction.** An agent already knows which entities its tools touched, so it can name them instead of paying a model to rediscover them.
* **Memory is routing context for the supervisor, not a fourth tool.** Nobody asks memory a question, and `recall` runs once per question rather than once per tool call.
* **It rewrites the question, not only the route.** Two failures seen in testing forced that, and both are below.
* **This is the first lab that writes to your graph.** Everything it writes is removable, adoption included, and the notebook's final section shows how.

== The Shape of the Agent

....
  Lab 5                          Lab 6

  question                       question -> recall
     |                                        |
  supervisor <--+                  supervisor <--+
     |          |                     |          |
     +-> genie / cypher / graphrag ---+ (unchanged)
     |                                |
  synthesize                       synthesize -> remember
     |                                             |
   answer                                       answer
....

`recall` searches what this team has said before, recent turns first. `remember` writes the question and the answer back, with the aircraft they mention.

The three tools are the ones xref:lab5.adoc[Lab 5] built, doing what they did there. The supervisor is the same node with a fourth variable in its prompt. Those are the only code changes between the two agents. Keeping the change that small is what lets the notebook compare memory-off against memory-on and attribute the difference to memory.

`recall` runs once per question, not once per tool call. Wire memory as a tool instead and the supervisor is free to call it three times in one turn, at several seconds each, for no extra information.

== Adoption: One Node in Both Halves

The memory library hangs conversations off `(:Entity {name, type})` nodes. Left alone it creates its own `N10004` beside yours, which leaves you with two stores that only a string comparison in Python can join.

**Adoption** stops that. It adds the `:Entity` label and the library's `id`, `type` and `name` properties to nodes you already have. Afterwards there is one `N10004`: still an `Aircraft` with its flights and maintenance events, and now also an entity a message can point at.

image::lab6-memory-graph.svg[Lab 6 memory graph,align=center]

Writing to nodes an earlier lab loaded makes this the one step in the workshop that changes existing data. Run the dry run, read the counts, then commit. Undoing it is a label strip rather than a delete, and the notebook's final section shows it along with the guard that keeps a memory cleanup from taking your fleet with it.

.Why the lab adopts `Aircraft` and refuses four other labels
[%collapsible]
====
Adopting everything looks like the better option: `System`, `Component`, `Sensor` and `Document` as well as `Aircraft`, for richer memory.

It breaks the graph. `adopt_existing_graph` sets `n.type` unconditionally, and those four labels already carry a `type` of their own, holding values like `Turbine` and `Engine` that Lab 2 and Lab 4 queries filter on. Adopting them overwrites every one of those with the string `COMPONENT` or `SYSTEM`. There is no error and no warning, and the queries that filter on `type` start returning nothing. Recovery is a full reload.

`Aircraft` has no `type` of its own, so adopting it overwrites nothing, and the query below needs `Aircraft` and nothing else. `memory.py` refuses the other four labels by name rather than relying on the notebook to get it right, and the notebook shows that refusal on purpose before it shows a successful adoption.

The same reasoning constrains what memory is allowed to create, though less sharply than it first looks. On its automatic extraction path the library adds an entity's type verbatim as a second label, so an entity of type `SYSTEM` becomes `:Entity:SYSTEM`. Neo4j labels are case sensitive, so that does not break `MATCH (s:System)`. What it leaves is an instance carrying both `:System` and `:SYSTEM`, differing only in case and holding unrelated things, which is a graph nobody can read six months later. The lab declares one entity type, `AIRCRAFT`, matched to the one label it adopts. On the explicit-mentions path the lab actually uses, the library adds no type label at all.
====

== The Query That Needs Both Halves

Three queries over the same graph, in order.

**The fleet graph alone**, ranked by critical maintenance events, is what a maintenance dashboard shows you. `N10011` comes last of six.

**The conversation memory alone**, ranked by how many different technicians asked, is what a memory product with no domain graph shows you. `N10011` is joint first.

Each list on its own says nothing unusual. An aircraft with few critical events is healthy. An aircraft several people asked about had a busy week. Read together they say something else: three technicians, on three separate shifts, each pulled the EGT trend on an aircraft the maintenance record calls healthy. Either they are seeing something the record has not caught, or three people each spent a shift on the same dead end. A supervisor wants to know about both, and neither list shows it alone.

One query returns that:

[source,cypher]
----
MATCH (u:User)-[:HAS_CONVERSATION]->(c)-[:HAS_MESSAGE]->(m)-[:MENTIONS]->(ac:Aircraft)
WITH ac, count(DISTINCT u) AS technicians, ...
MATCH (ac)<-[:AFFECTS_AIRCRAFT]-(ev:MaintenanceEvent)-[:AFFECTS_SYSTEM]->(sys:System)
----

The `(ac)` on the second `MATCH` is what makes this work. It is bound in the memory half and reused in the fleet half: the same node, with no join key, no federation and no second query. Without adoption, that `ac` would be a memory entity that happens to share a name with an aircraft, and joining the two would mean exporting both sides and matching strings in Python. String matching is where the tail number `N10011` and the tail number `n10011 ` stop matching each other.

== What Recall Has to Do Besides Search

Semantic search over past messages is the first job. Two more turned up during live runs, and both are described below.

=== Memory reached the router and never reached the tool

`recall` set `recalled`, the supervisor prompt rendered it, and the supervisor returned a route and nothing else. Lab 5's tools read the question text verbatim, which is Lab 5's documented contract, so a question saying "that aircraft" reached Genie as "that aircraft" and Genie replied asking which aircraft. Memory changed the route but not the answer, and the answer is what the lab claims memory improves.

.The fix, and why it lives in the supervisor
[%collapsible]
====
The supervisor now returns a third field alongside the route: the question with every reference to an earlier one replaced. `MEMORY_ROUTE_SCHEMA` requires it, so the same call that picks a tool also rewrites the question, and there is no extra model call.

The rewrite happens on the first pass only. After a tool has run, the question already carries the tail number, and rewriting an already-rewritten question lets it drift further from what was asked. The participant's original wording is kept in a separate `asked` field.

Lab 5's `tools.py` is untouched by all of this. The same mechanism would close a known Lab 5 defect, where a tool is handed the question rather than the finding, and doing that belongs in Lab 5 rather than here.
====

=== Semantic search cannot know what "that" means

The rewrite alone was not enough. Two things went wrong, and a debugging cell was needed to find each one.

**Every question the agent is asked is written to memory**, so the nearest neighbour to a question is very often that identical question, asked before. It scores near 1.0, it takes one of only three recall slots, and it carries none of what the supervisor needs, because the aircraft is in the reply and not in the question. Restatements of the question being asked are now dropped before the prompt sees them.

**Even then, a follow-up resolved to the wrong aircraft.** "Which system was that on?" is short and generic, so its nearest neighbours are whatever the busiest aircraft in memory happens to be. The setup question asked five seconds earlier scored lower than a week of seeded shift notes about a different aircraft. Semantic search finds text with related meaning, and "that" refers to whatever came last, which is a fact about time rather than meaning. So `recall` reads the conversation's own recent turns first and runs the search after them.

.The failure that was scored as a pass
[%collapsible]
====
The wrong-aircraft answer scored as resolved, because the scorer asked only whether the expected tail number appeared anywhere in the answer, and it happened to appear far enough down the text to be missed by the printed excerpt.

The scorer now requires the expected aircraft to appear and no other aircraft to appear. **The failure to catch is a confident answer to a question the agent misread**, which looks identical to a correct answer under a substring test. Read the answers as well as the score.
====

== Three Layers, and Which Ones You Write

`neo4j-agent-memory` splits memory three ways. These three names are the namespaces the code actually calls.

* **Short term.** The shift log. Messages, who said them, which entities they mention. This is what the lab's `recall` and `remember` nodes use.
* **Long term.** The permanent record. Preferences and durable facts that outlive a session.
* **Reasoning.** Traces, steps and tool calls: what the agent tried, what it touched, and whether it worked. A vector store has nowhere to put that.

Neo4j also publishes an earlier taxonomy that borrows LangGraph's semantic, episodic and procedural split. The workshop uses the one above because it is what the code participants run is built on.

The participant notebook writes short-term memory only. Long term and reasoning are shown in `02_instructor_demos.ipynb`, an instructor-driven notebook that ships to every workspace. It covers four cases: a correction that supersedes an earlier belief rather than contradicting it, a preference scoped to an aircraft rather than to a person, a shift handoff, and a reasoning trace the supervisor consults before it routes. That last case is the most interesting one, because a supervisor reading past traces routes on what has worked rather than on a fixed prompt.

== Going Further: Reasoning Traces

Short term is what the team said. Long term is what the agent knows. The third layer records what the agent **did**, and it is the layer a vector store has nowhere to put.

`neo4j-agent-memory` writes a `ReasoningTrace` per task, ordered `ReasoningStep` nodes under it by `HAS_STEP`, a `ToolCall` per step by `USES_TOOL`, and a `TOUCHED` edge from the step to every entity that step reached. Demo 4 records one trace by hand: a `cypher_node` call that failed, because the graph holds no time series, then a `genie_node` call that worked.

Reading it back is one query.

[source,cypher]
----
MATCH (:ReasoningTrace)-[:HAS_STEP]->(s:ReasoningStep)-[:USES_TOOL]->(tc:ToolCall)
MATCH (s)-[:TOUCHED]->(ac:Aircraft)
RETURN ac.tail_number AS aircraft, tc.tool_name AS tool,
       tc.status AS status, s.observation AS observation
ORDER BY tc.tool_name
----

Walking that path answers two questions that a log line cannot. **Which agent decisions touched this aircraft**, because the traversal starts at `ac` and every step that reached it is one hop away. And **which of those decisions failed**, because `tc.status` is on the tool call and `s.observation` records what came back. An incident review that starts with "why did the agent say that about `N10011`" runs as a query rather than a manual search through logs.

NOTE: `TOUCHED` hangs off the `ReasoningStep`, not off the `ToolCall`. The traversal is step to entity for the audit and step to call for the mechanics.

`MATCH (s)-[:TOUCHED]->(ac:Aircraft)` only resolves because the participant notebook adopted the fleet's `Aircraft` nodes. Without adoption the library writes its own `N10011` entity and the pattern returns nothing. That is the same dependency the query in the previous section has, showing up in a different query.

The library also keeps a running score per tool, `total_calls`, `successful_calls` and `failed_calls` on a `Tool` node, updated on every call. That is what a routing policy could read instead of a prompt.

== What Memory Costs

Memory adds latency to every turn. The notebook measures and prints it.

[cols="2,1"]
|===
| Operation | Cost

| `recall`, once per question
| 3 to 5 seconds

| `remember`, two messages written
| about 11 seconds

| Added per exchange
| about 15 seconds, and two `Message` nodes
|===

NOTE: Recorded 2026-08-08 to 2026-08-09, from job runs replaying a harness copy of `01_agent_memory.ipynb` against a live Aura instance and live Databricks Foundation Model endpoints. `worklog/lab6-memory-defects.md` is the record, and run `241421965631969` is the one these come from. Section 9 of the notebook reproduces the comparison.

Fifteen seconds a question is a good trade for a shift-handover agent, where the questions are few and the carried context matters. It is a bad trade for a high-volume endpoint answering one-shot lookups. Knowing the number lets you decide which case you are in.

Lab 6 writes on the hot path, during the turn, for teaching reasons: a participant who cannot watch the write happen cannot debug it. A production handover agent would move the write off the turn and accept stale memory in exchange, which replaces this question with "how far behind is memory right now?".

.What the graph itself costs
[%collapsible]
====
AuraDB Free caps at 200,000 nodes and 400,000 relationships. Memory adds a couple of dozen nodes per participant per session, so the node cap has plenty of headroom. The index count is the constraint to watch: the library installs a schema of its own on first connect, on an instance that already carries Lab 3's vector index.

`memory.py` names the four memory subsystems this lab never writes to, and the library then skips their indexes and constraints entirely. Facts, consolidation runs, read auditing and a geospatial point index are all left off. That keeps the combined schema small, and it is worth doing in any deployment where index quota is limited.
====

== One Endpoint, Redeployed

Lab 5 deployed this agent to a Model Serving endpoint. Lab 6 redeploys **that** endpoint with the two new nodes in it, rather than standing up a second one. An endpoint per participant is the tightest quota in the workshop, and the registered model name and the endpoint name are constants in Lab 5's `agent.py` for exactly this reason.

Memory adds no Databricks resource to the endpoint, because it writes to Aura, and Aura reaches the endpoint through environment variables rather than through MLflow's resource list. Lab 5 already set that up: the endpoint carries the Neo4j URI, username and password as secret references resolved at startup. Memory reads those same three variables, so the redeploy needs no new secrets and no second credential path.

== Why the Lab Installs a Pinned Fork

The lab installs `neo4j-agent-memory` from a wheel on a Unity Catalog volume, built from a fork, rather than from PyPI. The released version drops most `MENTIONS` edges when it extracts entities, with no exception and no warning, and `MENTIONS` is the edge the query above walks. The fork fixes that, and the fix has not gone upstream yet.

Reproducing this at work leaves you the same choice: wait for the fix to reach a release, or carry the patch yourself. The library is pre-1.0 and changes quickly, so treat an upgrade as a code change with its own test pass rather than a version bump.

Use explicit mentions whether or not the defect is fixed. Naming the entities yourself removes a model call from the critical path, the result is exact, and an agent already knows what its tools just touched. Use LLM extraction for text nobody has parsed yet.

== Where Memory Belongs

Databricks holds the telemetry, because timestamped values at that volume are cheap to scan there. Neo4j holds the topology, the history and now the memory. The same test decided all three placements: memory is relationship-rich, low-volume data whose value is in what it connects to, so it goes in the graph. Put it anywhere else and every question spanning both halves needs an export and a string match.
