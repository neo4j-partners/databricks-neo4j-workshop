= Databricks + Neo4j: Production AI Agents with Graph and Lakehouse

Databricks and Neo4j solve different halves of the same problem. Databricks is the Data Intelligence Platform: it governs and analyzes structured, semi-structured, and unstructured data at scale. Neo4j is the Graph Intelligence Platform: it makes the connections between entities explicit and traversable. Databricks handles volume and governance; Neo4j handles topology and traversal. Together they form a complete intelligence platform that AI agents can query through natural language.

This workshop builds a production AI system on that pairing: a multi-agent supervisor that routes each question to the platform built to answer it, then combines the results.

.**At a Glance**
* **Six labs, about five hours**, plus a take-home appendix on graph algorithms.
* **Two databases, one question box.** Neo4j Aura holds the fleet topology and the maintenance manuals; the Databricks Lakehouse holds the sensor telemetry.
* **You end with a LangGraph supervisor agent** you wrote, deployed to Model Serving as your own endpoint, with memory stored back in your graph.
* **Everything runs in a browser.** A Databricks workspace is provided; you create your own AuraDB Free instance in Lab 1.
* **The procedure lives in the notebooks.** These pages are the background behind them.

== What You Will Build

By the end of this workshop you will have a working AI system that answers natural language questions about a commercial aviation fleet. Ask it a question and a Supervisor Agent decides which backend can best answer it: Neo4j for relationship questions, Databricks for sensor trend questions.

The system handles two fundamentally different kinds of questions:

* **Relationship questions**: "Which components have had critical failures, and which flights did those failures delay?" These are best answered by traversing a graph in Neo4j.
* **Time-series analytics questions**: "How have engine temperature readings trended over the last 90 days?" These are best answered by running SQL over columnar data in Databricks.

One database handles one of those kinds well. This workshop pairs Neo4j and Databricks so each handles the workload it is built for, then connects them through a shared AI layer.

== The Aircraft Digital Twin Dataset

The workshop uses an Aircraft Digital Twin: a simulated aviation fleet with real structure, modeled over 90 operational days. Aircraft have systems and components. Components generate sensor readings and accumulate maintenance events. Aircraft operate flights between airports, and those flights can have delays tied to specific component failures.

The dataset includes:

* **Aircraft** with tail numbers, models, and operators
* **Systems** such as Engines, Avionics, and Hydraulics
* **Components** such as Turbines, Compressors, and Pumps
* **Sensors** with monitoring metadata
* **Sensor Readings**, hourly-scale telemetry over 90 days
* **Flights** with departure and arrival information
* **Maintenance Events** with fault severity and corrective actions
* **Airports** in the route network

The data speaks airline shorthand: sensor types like `EGT` and `N1Speed`, fault severities, and manual references such as ATA chapters. xref:glossary.adoc[The glossary] expands every term the labs use, and is worth keeping open in a second tab.

=== How the Data Splits Across Platforms

image::dual-database-architecture.svg[Dual Database Architecture,align=center]

The data splits across two platforms, each chosen for the workload it handles best:

* **Databricks Lakehouse** stores the time-series sensor telemetry: `sensor_readings`, plus the `sensors`, `systems`, and `aircraft` tables it joins against. Columnar storage and SQL make it ideal for aggregations, trend analysis, and statistical comparisons over large volumes of timestamped data.
* **Neo4j Aura** stores the knowledge graph: Aircraft, System, Component, Sensor, Flight, Delay, MaintenanceEvent, and Airport nodes connected by relationships such as HAS_SYSTEM, HAS_COMPONENT, OPERATES_FLIGHT, and HAS_EVENT, plus Document and Chunk nodes for GraphRAG retrieval over maintenance manuals. A graph traverses these multi-hop relationships natively, avoiding the expensive JOINs a tabular database would require.

Aircraft, Systems, and Sensors exist in both platforms as join points, kept in sync by the Neo4j Spark Connector. Many real questions span both stores, which is why the workshop builds a Supervisor Agent to route each one and combine the results. xref:databricks-platform.adoc[How Neo4j + Databricks Work Together] shows the SQL and Cypher query shapes side by side.

== What You Will Learn

The labs build on each other, moving from a single graph database to a full multi-agent system:

* **Lab 1** provisions Neo4j Aura and introduces Cypher, the graph query language.
* **Lab 2** loads the Aircraft Digital Twin into Neo4j from Databricks using the Spark Connector.
* **Lab 3** adds semantic search: chunk the maintenance manual, generate embeddings, and build GraphRAG retrievers.
* **Lab 4** builds a Genie Agent for sensor analytics, with an optional demo that turns it into a no-code Agent Bricks compound agent.
* **Lab 5** has you write the supervisor yourself in LangGraph, over Genie, your own graph and the Lab 3 retrievers, then deploy it to Model Serving.
* **Lab 6** gives that agent memory in Neo4j, so conversation history and maintenance history sit in one graph and one query can cross both.

== Architecture

The workshop lands on a **LangGraph supervisor agent that you write, deploy and own**, built in Lab 5 and given memory in Lab 6. A supervisor node reads each question and routes it to one of three tools: a Genie Agent for sensor telemetry in SQL, a Cypher query against your own Aura instance, and a GraphRAG retriever over the maintenance manuals. It is logged to Unity Catalog and served as a Model Serving endpoint that authenticates as a service principal.

image::lab5-agent-topology.svg[The Lab 5 supervisor routing to a Genie node, a Cypher node and a GraphRAG node over the Databricks Lakehouse and your own Aura instance,align=center]

Routing runs as a loop. Every tool returns its result to the supervisor, which can then pick another tool before it answers. That is how one question reaches both stores.

Lab 4 shows the same routing built a second way, without code. A **Supervisor Agent in Databricks Agent Bricks** sits over a Genie Agent and a governed Neo4j MCP connection. It stays an optional demo because the MCP server behind it is outside the scope of the workshop. xref:lab4.adoc[Lab 4] compares the two approaches side by side.

== Prerequisites

* A laptop with a modern web browser, and network access to Databricks and Neo4j Aura
* A Databricks workspace with Model Serving enabled, provided for the workshop
* An email address, for the AuraDB Free account you create yourself in xref:lab1.adoc[Lab 1]
* Basic familiarity with SQL and Python

No local software installation is required. Everything runs in the browser or in a Databricks notebook.
