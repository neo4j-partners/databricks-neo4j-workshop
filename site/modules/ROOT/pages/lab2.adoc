= Lab 2: Databricks ETL to Neo4j

In this lab you move data from Databricks Lakehouse into Neo4j using the Spark Connector. The Lakehouse holds aircraft fleet data as governed Delta tables; by the end, that same data will exist as a traversable graph of aircraft, systems, components, sensors, flights, and maintenance events.

TIP: Ready to start? Open `Lab_2_Databricks_ETL_Neo4j/01_aircraft_etl_to_neo4j.ipynb` in your Databricks workspace. Every step lives in that notebook; this page is the background behind it.

.**At a Glance**

* **Table rows become graph nodes**, foreign keys become relationships. The Spark Connector handles the mapping
* **Nodes load first**, then relationships. Both endpoints must exist before edges can be created
* **The lab notebook** builds aircraft topology (Aircraft, Systems, Components), then layers in Sensors, Flights, Delays, MaintenanceEvents, and Removals
* **Graph insights flow back** to the Lakehouse as enrichment columns in Gold Delta tables
* **Validation** compares node/relationship counts against source row counts to catch silent failures

== From the Lakehouse to the Graph

Only part of the Lakehouse moves to the graph. Aggregates, metrics, logs and documents stay in Delta. What projects into Neo4j is the subset whose connections you want to traverse. The Lakehouse stays the system of record, and the graph is a projection of those connections.

The mapping from tables to graph follows a few recurring patterns. The three diagrams below walk through the transformation using the aircraft data from Notebook 01.

image::step1-flat-tables-foreign-keys.svg[Flat CSV tables with foreign key columns linking rows across tables]

image::step2-spark-connector-mapping.svg[Spark Connector mapping DataFrame rows to graph nodes and relationship rows to edges]

image::step3-connected-graph.svg[The resulting connected graph with a SQL vs Cypher comparison]

* **Rows become nodes.** A row in the aircraft table becomes an Aircraft node, with columns like `aircraft_id`, `model`, and `status` as node properties.
* **Foreign keys become relationships.** A column like `system.aircraft_id` pointing to `aircraft.aircraft_id` becomes `(:Aircraft)-[:HAS_SYSTEM]->(:System)`. These are straightforward one-hop lookups that SQL also handles well.
* **Mapping tables become relationships.** A junction table like `component_removals` produces no nodes at all. Each row becomes a `REMOVED_FROM` relationship with `removal_date` and `reason` as relationship properties. The mapping table disappears entirely.

.Shared attributes and self-referential patterns
[%collapsible]
====
* **Shared attributes become shared nodes.** Two aircraft operating at the same airport have no foreign key between them. Discovering that link in the Lakehouse requires a self-join. In the graph, Airport becomes a shared node and both aircraft connect to it, making the hidden connection explicit and traversable.
* **Self-referential columns become chains.** `origin_airport` and `destination_airport` in a flights table point to two entities in the same table. In the graph this becomes `(:Airport)<-[:DEPARTED_FROM]-(:Flight)-[:ARRIVED_AT]->(:Airport)`. Chains of these are natural traversals in the graph but require complex nested joins in SQL.

The graph advantage grows with each pattern:

* **Foreign keys** are simple one-hop lookups.
* **Mapping tables** eliminate multi-table joins.
* **Shared attributes** reveal hidden networks.
* **Self-referential chains** replace complex nested joins.
====

== ELT: Lakehouse to Graph

Raw data lands in cloud storage such as S3, ADLS Gen2 or GCS, which is the unprocessed landing zone. Databricks processes that raw data into Delta tables via Jobs, Notebooks, or Spark Declarative Pipelines. Delta tables are the interchange format; the Neo4j Spark Connector reads from these governed tables.

.Delta Lake schema enforcement
[%collapsible]
====
Delta Lake enforces schema and rejects bad data at ingestion: column renaming, type casting, and validation happen here so that graph properties are clean without extra transformation downstream.
====

=== The Neo4j Spark Connector

The Spark Connector is the officially supported bridge between Databricks and Neo4j. It turns Lakehouse rows into graph nodes and relationships, and pulls graph data back into DataFrames for analytics or ML. It supports batch and incremental loading patterns.

* **Node loading** maps DataFrame columns to node properties. Each row becomes a node through a batched upsert, which creates the node if it is new and updates it if it already exists. That makes the load idempotent. The connector uses `labels` and `node.keys` options to control which label the node gets and which property serves as its unique identifier. Nodes load first because both endpoints must exist before relationships can be created.
* **Relationship loading** matches existing nodes by property values and creates the specified relationship type between them. Transaction details or operational metadata ride as properties on the relationship itself; no separate edge table, no foreign key resolution at query time.

.Does the data have to move?
[%collapsible]
====
Three paths connect the two platforms, and only one of them copies data.

* **Spark Connector**, what this lab uses. It copies: Delta rows become nodes and relationships inside Neo4j. Pick it when you want a graph that persists, traversal speed at scale, or graph algorithm results written back to Delta.
* **Virtual graph**. Cypher in, SQL out. Neo4j tooling queries Delta tables where they already sit.
* **Neo4j Unity Catalog Connector**. SQL in, Cypher out. Analysts and BI tools query the graph as SQL, with no Cypher to learn and no copy in the lakehouse.

The last two read data where it already lives. This lab copies, because every lab after this one traverses the graph and expects it to be there. See xref:databricks-platform.adoc[How Neo4j + Databricks Work Together] for all six integration patterns.
====

=== Design Decision: Relationship Types vs. Properties

.When to use typed relationships vs. generic relationships with properties
[%collapsible]
====
A common modeling choice: use one relationship type per connection kind (`:TRANSFERRED_TO`, `:SHARED_DEVICE`) with indexed type lookups and faster traversal, or use a generic type with a property (`:CONNECTED {type: "transfer"}`) for a simpler schema but slower property filters. Default to type per connection when traversals follow specific connection types. Neo4j relationships are directional, so bidirectional flows require writing in both directions.
====

=== Validation

The connector reads from Neo4j just as easily as it writes, returning Cypher results as standard DataFrames. Three checks cover the common failure modes: node counts should match source row counts, relationship counts should fall within expected ranges, and high-connectivity nodes should reflect known patterns from the source data.

.Debugging count mismatches
[%collapsible]
====
If counts do not match, the most common causes are failed node loads or key value mismatches. The connector silently drops relationships when the MATCH clause can't find the target node.
====

== Graph Insights Flow Back to the Lakehouse

Graph-derived metrics become columns in Delta Gold tables, available for dashboards, ML features, and downstream analytics.

.Graph algorithm examples
[%collapsible]
====
* **Cycle detection** identifies entities involved in circular chains.
* **PageRank** scores influential nodes for risk prioritization.
* **Louvain community detection** clusters tightly connected entities into groups.
* **Degree centrality** counts connections as ML features.

Once in Delta Lake, these scores join with operational data that never left the Lakehouse. That join happens in the Gold layer, where the graph-derived columns sit beside the columns Databricks computed.
====

== Databricks Compute and Notebooks

In Databricks, **compute** refers to a managed cluster of virtual machines that provides the Spark runtime needed to execute code. Your workshop compute comes pre-configured with Apache Spark, the Neo4j Spark Connector, and the Python packages required by the lab notebooks.

A **notebook** is an interactive document of cells containing Python, SQL, or markdown. You run cells sequentially, and each cell displays its output inline. Notebooks are the primary interface for the ETL work in this lab.

== What You Load

**Notebook 01** builds the core aircraft topology first:

----
(Aircraft) -[:HAS_SYSTEM]-> (System) -[:HAS_COMPONENT]-> (Component)
----

Topology loads in order: Aircraft nodes, then System nodes (Engines, Avionics, Hydraulics per aircraft), then Component nodes (fans, compressors, turbines, pumps) attached to each system.

The notebook then layers operational and maintenance data on top of that topology: Sensors attached to systems, Flights operated by aircraft, Delays on flights, MaintenanceEvents affecting components (with `AFFECTS_SYSTEM` and `AFFECTS_AIRCRAFT` back-links for cross-cutting impact queries), and Removals that link aircraft to removed components. It also loads the canonical `OperatingLimit` rows and attaches each one to the sensor it governs.

The whole shape, once the notebook finishes:

----
(Aircraft) -[:HAS_SYSTEM]-> (System) -[:HAS_COMPONENT]-> (Component)
(Aircraft) -[:HAS_SYSTEM]-> (System) -[:HAS_SENSOR]-> (Sensor)
(Sensor)   -[:HAS_LIMIT]-> (OperatingLimit)
(Aircraft) -[:OPERATES_FLIGHT]-> (Flight) -[:DEPARTS_FROM / :ARRIVES_AT]-> (Airport)
(Flight)   -[:HAS_DELAY]-> (Delay)
(Component) -[:HAS_EVENT]-> (MaintenanceEvent)
(MaintenanceEvent) -[:AFFECTS_SYSTEM]-> (System)
(MaintenanceEvent) -[:AFFECTS_AIRCRAFT]-> (Aircraft)
(Aircraft) -[:HAS_REMOVAL]-> (Removal) -[:REMOVED_COMPONENT]-> (Component)
----

Lab 5 uses `HAS_LIMIT` directly. Every question of the form "is this reading out of limits?" walks from a `Sensor` to its `OperatingLimit` and compares the two. The comparison works on a plain string because the units match on both sides by design: `EGT` is `°C` in the sensor metadata and `°C` in the limit table, and `N1Speed` is `% RPM` in both.

== Sensor Readings Stay in Databricks

**Lab 2 loads no `Reading` nodes into Neo4j.** The sensor telemetry stays in Delta. Neo4j gets the things worth traversing: which aircraft, which system, which sensor, which limit, which maintenance event. The readings are a columnar aggregation workload, and Delta scans them cheaply.

This split is why Lab 4 uses a Genie Agent and why Lab 5's agent routes between backends instead of picking one. Traversal cannot answer a question about EGT trends. SQL cannot answer a question about which components a fault cascaded into.

== The Load Clears the Database First

The notebook runs with `CLEAR_DATABASE = True`. Nodes are written in Append mode, a plain `CREATE`, which never replaces an existing node, so running the load twice would give you two of everything. Clearing first is what makes the load repeatable: a participant who gets halfway and stops can start the notebook again from the top and land in a known state.

The cost is that your Aura instance cannot hold anything else you want to keep. Re-running Lab 2 deletes whatever Lab 3 or Lab 6 wrote alongside it.

== Key Concepts

1. **Unity Catalog Volumes** store files accessible from notebooks
2. **Nodes first, relationships second** ensures endpoints exist before connections are created
3. **Cypher queries from Databricks** verify data loaded correctly by checking node and relationship counts against source row counts
